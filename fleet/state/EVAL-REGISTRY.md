# EVAL-REGISTRY — consult-first tool/library evaluation registry

**Consult this BEFORE any new tool research.** Before researching, adopting, rejecting, or
re-litigating any external tool/library (or re-deciding a prior internal build-vs-adopt call),
grep this file for the tool name first. A new evaluation MUST add a row here with its
`alignment` honestly classified (see column definitions below) — citing an existing ALIGNED
row as settled is fine; citing a DRIFTED or MIXED row as settled is not (re-test it against
the framing it skipped, per its `reason`). This file is append-only; git history is the audit
trail. Seeded 2026-07-13 from `fleet/state/EVAL-REGISTRY-RECONCILE.md` (do not delete that
file — it is the full reasoning trace behind the LiteLLM rows below).

## Schema

`tool | scope | date | verdict | alignment (aligned/drifted/mixed/n-a) | reason | evidence-link | supersedes`

- **aligned** — the eval actually tested the real framing for its scope (e.g., for a
  plugin-wrap question, it tested plugin-wrap — not just full-embed-vs-hand-roll), and its
  verdict can be treated as settled.
- **drifted** — the eval rejected/accepted using a strawman (e.g., "heavy dependency conflicts
  with stdlib-only core" without checking whether Charon's existing wrap-as-optional-plugin
  pattern — Presidio, OpenTelemetry — resolves that exact objection). Re-test before trusting.
- **mixed** — some reasoning in the eval is aligned, some is drifted/unresolved; read the
  `reason` column before treating as closed.
- **n-a** — tangential/informational mention, not itself a verdict on adopting the tool.
