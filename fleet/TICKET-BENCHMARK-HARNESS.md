# TICKET — BENCHMARK-HARNESS: make MODEL-BENCHMARK-SPEC.md runnable + first run

**Type:** build-rig (fleet tooling — NOT product; never touch `src/charon` product code except read-only fixtures)
**Recommended model:** Claude **Opus** (the graders are correctness-critical — a grader that doesn't truly discriminate makes the whole benchmark worthless; this is the exact skill the benchmark itself tests). Build as a Claude sub-session, not a manual opencode droid (a droid building the graders would itself need grading — chicken-and-egg).
**Depends on (both exist):** `fleet/MODEL-BENCHMARK-SPEC.md` (section definitions S0–S6, S6 = frontend), `fleet/model-scorecard.sh` (ledger; bench-row schema).

## GOAL
Turn the benchmark SPEC into a RUNNABLE, deterministically-graded harness that scores a coding model 0–100 per section (S0–S6, including the new S6 frontend section) and **auto-appends** `bench` rows to `model-scorecard.tsv` — with no manual scoring step. The harness must be fast enough and easy enough to run against **many** models back-to-back, not just the two pilot models. Then do a first run of **glm-5.2** and **deepseek-v4-pro**.

## DELIVERABLES (all under `fleet/benchmark/`)
1. **Fixtures** — for each section S0–S6 in `MODEL-BENCHMARK-SPEC.md`, a self-contained fixture: a minimal repo state / injected bug / task setup the model works against, plus the "golden" expected outcome. S6's fixture is a **separate small frontend repo** (`fixtures/status.json`, bare `index.html` mount point, preconfigured build toolchain) per the spec — do not conflate it with the backend `bench-fixture/` repo. Read the spec for each section's exact task + objective checks. Keep fixtures small.
2. **Deterministic graders** — one grader per section, 0–100, NO LLM-judge. Each must implement the spec's objective checks, e.g.: the model's test FAILS on the buggy fixture and PASSES on the fixed one; `charon gate` passes; only the intended files changed (diff-scoped); the real-path proof (e.g. S2: grader mutates the config and re-runs the model's own test so a dodged/inert feature scores 0; **S6: grader loads the built bundle in jsdom, stubs `fetch`, asserts the rendered DOM matches the fixture, then re-runs against a MUTATED fixture and asserts the DOM changes — a hardcoded/static component scores 0 on this check**). Partial-credit bands per the spec. The grader takes the model's produced worktree/diff and emits a score + reason. Every grader run is fully scripted — **no human reads a diff and assigns a number.**
3. **Runner** — `fleet/benchmark/run.sh <model>`: loops **all sections S0–S6** for the given model — for each section: (a) prepare the fixture in an isolated worktree, (b) present the section's task PROMPT for the model (see model-driving seam below), (c) once the model has produced its attempt, run the grader, (d) `model-scorecard.sh append <date> bench <section> <work_class> <tier> <model> <verdict> <gate> <score> "<note>"` — **this append is automatic, part of `run.sh`, never a separate manual step.** Print a per-model summary: tier reach = highest section cleared above its class floor (backend ladder) plus the S6 frontend score/tier reported alongside (S6 is a parallel axis per the spec, not folded into the backend tier).
4. **Many-models support** — `run.sh` MUST accept a single `<model>` arg for a one-off run, AND the deliverable includes a thin wrapper, `fleet/benchmark/run-many.sh <model1> <model2> ...` (or a `--models-file <list>`), that loops `run.sh` over a LIST of models back-to-back in one invocation, auto-appending all their rows to the same `model-scorecard.tsv` and printing one combined summary table at the end. This is the seam that lets the manager benchmark a new model roster in a single command rather than one session per model.
5. **Fast-to-run** — each section must be **time-boxed**: the runner enforces a per-section wall-clock cap (skip/timeout → score 0 + `note="timeout"`, never hang waiting on a model). `run.sh` must support running a **subset of sections** (e.g. `run.sh <model> --sections S0,S2,S6`) so a quick smoke/re-check doesn't have to pay for the full ~61-min, 7-section budget every time. Document the expected wall-clock budget per section (from the spec's Time column) and the full-run vs. subset tradeoff.
6. **Model-driving seam** — for now, driving the model is MANUAL (matches the current opencode-tab flow): `run.sh` prints each section's prompt + the fixture worktree path; the operator pastes it into an opencode tab (model selected) pointed at that worktree; `run.sh --grade <section> <model>` then grades what's there **and auto-appends the score row** — grading and ledger-append are never separate manual steps, even in the manual-driving flow. DESIGN this as a clean seam so a future headless opencode/gateway driver can slot in without reworking the graders (this is also what unlocks true many-models-unattended runs later). Document the manual steps.
7. **First run** — run all 7 sections (S0–S6) for **glm-5.2** and **deepseek-v4-pro**, append their `bench` rows, and report the two scorecards. (If full manual driving is impractical in one session, at minimum build+self-test the graders against the golden fixtures — prove each grader gives 100 on the golden-fixed and 0 on the golden-buggy/inert one — and leave the model runs as a documented next step.)

## ACCEPTANCE CRITERIA (explicit — the harness is NOT done until all of these hold)
- [ ] **Fast:** a single section run completes within its documented time-box; a hung/unresponsive model run is capped, not left open-ended; a `--sections` subset flag exists so a partial re-check doesn't require a full 7-section run.
- [ ] **Many-models:** `run.sh <model>` runs unattended through S0–S6 for one model; `run-many.sh <model1> <model2> ...` (or `--models-file`) runs the full section set for a LIST of models back-to-back in one invocation with no per-model manual re-invocation of the runner.
- [ ] **Auto-scoring:** every grader emits its score programmatically and `run.sh`/`run-many.sh` appends the `bench` row to `model-scorecard.tsv` as part of the run — there is no step where a human reads output and manually types a score into the TSV.
- [ ] **S6 included:** the frontend section (fixture, grader, prompt) is implemented per `MODEL-BENCHMARK-SPEC.md` §3 S6, including the jsdom render check and the mutated-fixture real-data-proof check; S6's grader is self-tested the same as S0–S5 (100 on a golden Svelte solution AND on a golden vanilla-JS fallback solution — the grader must not be framework-specific; 0 on a hardcoded/static solution that fails the real-data proof).

## MUST / BOUNDARY
- Graders MUST be self-tested: prove each gives ~100 on the golden-correct solution and low/0 on the inert/buggy one. A grader that can't distinguish them is a bug. (S6's self-test additionally proves the grader accepts both a Svelte and a vanilla-JS golden solution, since the spec allows either.)
- No product-code edits; fixtures may COPY/read product code but the harness lives in `fleet/benchmark/`. No secrets/keys.
- Deterministic only — re-running a grader on the same worktree gives the same score.
- No manual scoring anywhere in the happy path — if a human has to read a diff and assign a number, that's a bug in the grader, not an acceptable fallback.
