# ADR-POOLS — Collapse ~50 hand-maintained pools into 4 tier-pools + a derived-routing grades table

- **Status:** Proposed (2026-07-07) — design-only, no code/push. Feeds the next adversarial review.
- **Deciders:** Rafael (operator) — target design is operator-decided; this ADR documents and grounds it, not re-litigates it.
- **Supersedes:** `docs/adr/0004-routing-gateway-roles-pools-frontend.md` D4 (`role → ordered pool` schema) and its R2 amendment (`.charon/models.json` + `.charon/pools.json` flat-array schema). D1–D3, D5–D8 of ADR-0004 are UNCHANGED (agent selection, exhaustion detection, orchestration, frontend, hermes cherry-picks all stand).
- **Relates to:** ADR-0005 (gateway-first; `vid→pool→provider` failover core — UNCHANGED, this ADR changes what feeds the pool, not the failover mechanism), ADR-0014 (engine consumes gateway failover for tier selection via a *tier vid* — this ADR makes "tier vid" a first-class, benchmark-backed concept instead of an ad hoc per-run pool).
- **Grounded by:** `fleet/scratch/pools-analysis.md` (live sprawl audit, read-only against 4-LOM), `fleet/scratch/pools-origin-attribution.md` (why it's shaped this way), `fleet/scratch/research-litellm-bifrost.md`, `fleet/scratch/research-opencode-ecosystem.md`, `fleet/scratch/research-gateway-landscape.md` (borrowed-pattern survey), benchmark-v2 (`fleet/HANDOFF-2026-07-06.md`, `model-scorecard.tsv` — S0–S6 work-classes, Frontier/Strong/Capable/Basic tier labels, live-validated against gpt-5.4).

## Context

### The sprawl (what exists today)
Live 4-LOM gateway (`/data/pools.json`+`models.json`+`providers.json`, `ghcr.io/slop-platform/charon:v0.3.6`):

- **50 pools**, 201 model routes, min 2 / median 4 / max 7 members each.
- **82% of the 49 non-`auto` pools (40/49) are one of exactly two boilerplate templates** — `{zen, go, nanogpt, openrouter}` fan-out or the same shape for a `-free`-*named* model — applied per model family by hand. Adding one model means hand-writing ~4 `models.json` entries + 1 `pools.json` array that's 90% copy-paste of an existing pool.
- **`cost_rank` is inert for ~95% of routes** (falls through to the neutral default `1000`; only 9/201 routes have a differentiated rank). The *real* priority signal is raw array order in `pools.json` — proven by the existence of a whole "zen-demote" backup+edit session whose only purpose was reordering array elements, not changing membership.
- **2 pools provide no real failover** (`big-pickle`, `gpt-5.3-codex-spark`) — both members are the same opencode-zen account under two aliases, not independent providers.
- **Three separate, not-mechanically-linked "curated model list" concepts** coexist with no enforced relationship: (1) the 50 gateway pools, (2) opencode's `charon`/`charon-full` provider profiles (client-side, regenerated by `regen-charon-models.sh`, hand-curated 30-id subset that does NOT auto-track pool membership), (3) `model_catalog.py`'s independent 15-entry `tier_hint` catalog used only by `charon tier`/`charon setup`'s CLI picker. Drift between these is already logged (`dead-free-go-prune-report.md`, `reds-triage.md`).

### Why it's shaped this way (attribution)
The pool *model* — `PoolEntry`, free-first/cost-rank stable sort, the flat `pools.json`/`models.json`/`providers.json` schema — was designed end-to-end by Claude Opus 4.8 in one tight arc (ADR-0004, same commit as MVP #1, `13b6ccf`). Every session since — 15+ dated live-data edits and code patches (SR-6's `derived_cost_rank` fix by GLM/DeepSeek, `POOLS-EDIT-PLAN.md`'s hand-authored curl templates, `zen-demote`/`dead-free-go-prune` single-pool edits) — **pattern-matched the existing per-model-array shape instead of abstracting it.** No consolidation commit exists anywhere in git or `fleet/`. SR-6 in particular is a cautionary precedent directly relevant to this ADR's mechanization section: it shipped **inert for months** because `add_model`/`add_models_bult` kept stamping the default `1000` on every new entry — a real signal that silently never took effect. Any redesign must not repeat that failure mode.

### Constraints (unchanged, load-bearing)
- **Standalone**: ships as a single Python venv/binary, no new runtime dependency (no Postgres/Redis/network router service).
- **Provider-agnostic / agent-agnostic**: not hardcoded to any one provider or ACP agent (ADR-0014).
- **Free-first**: cost minimization is a first-class routing input, not an afterthought.
- **INV-P0**: adding a backend/provider/model is a **config/data** change, not a **code** change.
- **No hosted routing dependency**: every borrowed pattern below is self-hostable (Apache-2.0/MIT/open-weight); no SaaS router (Unify, Not Diamond, Requesty, OpenRouter `auto`) becomes a hard dependency of the tier engine.

## Decision

**Collapse the ~50 hand-authored pools into exactly 4 TIER-pools — Frontier / Strong / Capable / Basic — each a plain SET of model ids, fed by ONE `model → {tier, per-work-class grades}` table.** Routing is **derived**, never enumerated:

1. A client (or the engine, per ADR-0014) requests a **primary model id** (+ optional work-class).
2. The gateway tries the primary. On failure (429/402/5xx/pseudo-success downgrade, per ADR-0004 D5), it looks up the primary's **tier**, and selects the **best remaining model in that tier for the declared/inferred work-class** — free/cost as tiebreak, a live-health signal decides "who wins right now" among equally-graded candidates.
3. If the whole tier is exhausted, cascade down one tier (Frontier → Strong → Capable → Basic) and repeat.
4. **Adding a model = one row in the grades table.** No new pool, no hand-written fan-out, no per-model `pools.json` array.

This directly kills the two structural defects `pools-analysis.md` names: (a) the 82%-boilerplate-template sprawl (§5.1: "a `for any model, try [zen→go→nanogpt→openrouter] unless overridden` default rule would collapse ~40 of the 50 pool entries... with zero loss of routing behavior" — never done until now), and (b) the inert-`cost_rank`/list-order-as-hidden-priority hack (§5.2) — replaced by an explicit, benchmark-derived grade plus an explicit live-health tiebreak, so priority intent is data, not JSON array position.

## Design detail

### The 4 tiers
Frontier / Strong / Capable / Basic — **these labels already exist and are live-validated**, not invented for this ADR: benchmark-v2's `tier_chart.py::composite_v2()` already produces exactly these four labels (+ "No-Tier") from a model's S0–S6 composite score, and the first real run (`gpt-5.4 → FRONTIER, composite 95.8`, `fleet/HANDOFF-2026-07-06.md`) proves the mechanism works end to end. A tier is a **set membership derived from a model's composite grade crossing a documented cut**, not a hand-curated list — the same anti-boilerplate principle applied one level up.

### The grades table
One `model → { tier: Frontier|Strong|Capable|Basic, provider_routes: [...], work_class_grades: {S0..S6: score|null}, cost: {free: bool, cost_rank: int}, health: {...} }` table replaces `pools.json` + the boilerplate 82% of `models.json`. Data sources, each additive and offline (no runtime network dependency on the hot path):

1. **Benchmark-v2** (`model-scorecard.tsv` → `tier_chart.py`) — the primary quality signal. Its S0–S6 sections ARE the work-classes this ADR routes on (`bugfix, money-path, routing, ci-infra, refactor, greenfield-feature, frontend`); its composite formula (mean(S1–S6), `COMPOSITE_EFF_CAP=±2` efficiency-tiebreak-only, hard source/season partitioning) already produces the tier cut. Import path: periodic `tier_chart.py --source bench2 --season <id>` run feeds the grades table; provisional (open-season) scores render "still OPEN (provisional)" and must not silently promote a tier (mirrors the SR-6 lesson: an unproven signal must not act as if proven).
2. **Public benchmarks** (LMArena/MMLU/HumanEval-class, per `research-gateway-landscape.md`'s RouterBench survey) — fills grade gaps for models not yet run through benchmark-v2, and is the validation harness (Martian's **RouterBench**, open dataset+repo, self-runnable) used to sanity-check that the derived tier assignment actually beats the old static ordering before cutover.
3. **models.dev pricing import** (`research-opencode-ecosystem.md` §1) — a periodic, opt-in `charon models refresh-pricing` offline import of the static `models.dev/api.json` snapshot backfills `cost.input`/`cost.output` so `cost_rank` is computed from real prices instead of the current inert `1000` default. This is the fix SR-6 attempted and left inert — this ADR makes it a **data import**, not a formula patch layered on the same boilerplate shape, and ties its correctness to acceptance gate (a) below so it cannot go inert silently again.
4. **Live actuals/health ledger** (à la Unify's two-signal design and TokenWise's per-call ledger, both `research-gateway-landscape.md` / `research-opencode-ecosystem.md`) — a local-first JSONL/SQLite ledger recording each attempt's actual outcome (success/fail, latency, cost, cooldown state), separate from the static grade. This is the "who wins **right now**" signal: static grade decides tier placement (slow-changing), the live ledger decides which same-tier, same-work-class member is tried first *today* (fast-changing — a provider mid-outage drops to the back without needing a benchmark re-run). This borrows Unify's exact "static-benchmark-score × live-runtime-telemetry" split, self-hosted, no SaaS dependency.

### The routing algorithm
```
request(primary_model, work_class=None):
  try primary_model
  on failure (429/402/5xx/model-field-mismatch per ADR-0004 D5):
    tier = grades[primary_model].tier
    wc = resolve_work_class(work_class, primary_model)   # see below
    candidates = [m for m in grades if m.tier == tier and m.id != exhausted]
    rank candidates by: work_class_grade[wc] desc, then free desc,
                         then cost_rank asc, then live_health desc
    try best candidate; repeat on failure, excluding tried
  on full-tier exhaustion:
    cascade to next tier down (Frontier→Strong→Capable→Basic); repeat
  on all-tiers-exhausted: terminal failure (unchanged from today's
    all-excluded clean-raise contract, ADR-0004 R2)
```
This reuses, not replaces, ADR-0004 D5's exhaustion detection and ADR-0014 D1/D2's gateway-resolves-a-vid pattern — a "tier vid" in ADR-0014's sense becomes a **real, benchmark-backed set**, not an engine-constructed ad hoc pool.

### The work-class crux — 3 options, recommendation
Work-class (which S0–S6-shaped job this request is) determines which grade column ranks candidates. Three ways to get it, borrowed from the router landscape survey:

1. **Client-declared header** (e.g. `X-Charon-Work-Class: refactor`) — zero latency, zero extra compute, trivially self-hostable (it's just a header). Requires the client to know/declare its own work-class; today's clients (opencode, curl, any OpenAI-compatible caller) do not.
2. **Arch-Router self-hostable classifier** (Katanemo, open-weight 1.5B, 93.17% in-paper accuracy, policy-based — classifies into *operator-defined* work-class policies without retraining when models change, `research-gateway-landscape.md` §3) — automatic, no client changes required, but adds a local inference call on the failover path (latency + one more moving part) and is unproven against Charon's own S0–S6 taxonomy specifically.
3. **Infer-from-primary** (use the primary model's own strongest grade as a proxy for "what this request probably is") — zero extra cost, but systematically biased (a request routed to a coding-specialist primary looks like a coding job even if it's a docs task) and gives no signal at all on a cold/first request to an unfamiliar model.

**Recommendation: declared-overrides + Arch-Router fallback + a GENERALIST default, in that priority order.** If the client declares a work-class, honor it (option 1, zero-latency, zero new dependency). If not declared, run Arch-Router locally to classify (option 2) — self-hostable, no SaaS call, matches the constraint set. If Arch-Router is unavailable/unconfigured (e.g. minimal install), fall back to a **GENERALIST** work-class column (the model's mean grade across S0–S6, not any single section) — this guarantees the new system is **never worse than today's undifferentiated pool order**, satisfying the "no regression" bar without requiring every deployment to run a classifier model. Option 3 (infer-from-primary) is explicitly NOT the fallback — its bias failure mode is worse than a neutral generalist average.

## Borrowed patterns (design references only — zero runtime dependency)

| Pattern | Source | What Charon borrows |
|---|---|---|
| Group-by-capability instead of hand-listed membership | LiteLLM `model_name` groups, Bifrost `allowed_models` | The core "shared tag, not shared array" idea — this ADR's tier-as-set IS this pattern, one level up (tier instead of per-role pool) |
| Quality-gradient routing, published methodology | RouteLLM (LMSYS, Apache-2.0, local OpenAI-compatible server) | Reference for "is the top tier actually needed for this query" — validates the cascade-down-tiers design; not embedded, its methodology (preference data → win-rate score) informs how benchmark-v2 grades could later be refined |
| Static-benchmark-score × live-runtime-telemetry two-signal split | Unify.ai (concept only — SaaS, likely discontinued, no code borrowed) | Directly structures this ADR's "grade decides tier, live ledger decides who-wins-now" split |
| Work-class / policy classification without retraining | Arch-Router (Katanemo, open-weight, self-hostable) | The auto-classify fallback in the work-class recommendation above |
| `label → {primary, fallback[], max_cost, max_latency}` policy schema | Requesty (schema only — SaaS, not adopted as a dependency) | Candidate shape for how a declared-work-class override could be expressed in config |
| Public validation dataset/harness | RouterBench (Martian, open, self-runnable) | Used to prove the derived-tier design actually beats static ordering before cutover (acceptance gate, see Mechanization) |
| Upstream-maintained model/provider metadata catalog | Helicone AI Gateway `providers.yaml` (Apache-2.0) | Precedent for pulling pricing/capability metadata from an externally-maintained source (models.dev fills this role for Charon) rather than hand-typing it |

Explicitly **not** adopted as runtime dependencies: LiteLLM (wrong language/stack, wants Postgres+Redis at scale), Bifrost (Go, best routing gated enterprise), any SaaS router (Unify/Not Diamond/Requesty/OpenRouter `auto` — closed, hosted, violates provider-agnostic + no-hosted-routing-dependency constraints). OpenRouter `auto` may optionally be exposed as a passthrough model id for users who explicitly want it, but the tier engine is never built on top of it.

## Options considered

### Option A (REJECTED, steelmanned): generate the 50 pools from a template
Keep the `pools.json`/`models.json` flat-array schema exactly as-is, but stop hand-authoring entries — instead run a generator that expands `(model families) × (provider-route templates)` into the same 50-pool shape mechanically. **Steelman:** this is the *smallest possible diff* — zero schema change, zero consumer breakage (`_build_routes_and_pools`, the setup API, `status_snapshot()`, `regen-charon-models.sh` all keep reading the exact same file shape), and it directly kills the *authoring* pain (82% boilerplate) that `pools-analysis.md §5.1` names as the top complexity source, with the least engineering risk of any option in this ADR.

**Why REJECTED (operator decision, not re-litigated here):** it still produces ~50 pools — a generator that emits 50 boilerplate entries is not materially different from 50 hand-written ones from the *consumer's* perspective: the setup API still CRUDs 50 pool objects, the dashboard still renders a 50-row pools table, `_tier_pools`'s merge point still reconciles against 50 keys, and every future "add a work-class-aware grade" feature has to be retrofitted onto 50 pool objects instead of one table. It solves the authoring-toil symptom while leaving the too-many-pools structural problem (the actual complaint) untouched, and it does nothing for the inert-`cost_rank`/hidden-list-order problem (§5.2) — a generator still needs *some* priority signal per template slot, and nothing in Option A supplies one better than today's array order. It is a real, safe, defensible incremental step — which is exactly why it must be named and rejected explicitly rather than silently dropped, so the adversarial reviewer can attack the rejection, not just the chosen design.

### Leverage OpenRouter `auto` — optional passthrough only, not a design foundation
`openrouter/auto` (confirmed powered by Not Diamond, `research-gateway-landscape.md` §3) could be exposed as one more model id in Charon's existing OpenRouter integration at near-zero build cost. Rejected as a foundation: closed SaaS meta-model, zero pre-call visibility into which model was actually picked, locks routing quality to OpenRouter's curated ~19-model pool (excludes NeuralWatt/NanoGPT/direct providers Charon already has), and violates the provider-agnostic mandate if the tier engine depended on it. **Kept only as an optional pass-through model id** for operators who explicitly want to try it — never wired into the tier/grade routing path itself.

## Blast radius + phased migration

Everything `pools-analysis.md §4` names as a consumer of the current pool *structure*:

- `gateway._build_routes_and_pools` (the compiler) and `derived_cost_rank` — must be re-pointed at the grades table instead of `pools.json` arrays; the free-first/cost-rank stable-sort *contract* stays, its input source changes.
- `_tier_pools` (the second, `tiers.json`-fed compiler merging into the same `pools` dict) — its merge point must keep working against the new 4-tier shape; this is a natural convergence point since it's already named "tier".
- Global fallback-provider synthesis (`gateway.load_config`) — behavior of "append fallback to every route not already pooled" needs redefinition once "pooled" means "tier-member" instead of "named pool member."
- `/charon/{providers,models,pools,tiers,...}` setup API + its inline JS dashboard — CRUD surface must migrate from "CRUD 50 pool objects" to "CRUD grades-table rows + 4 fixed tier sets"; this is the largest UI-facing change.
- `GatewayProxyServer` cooldown scope (keyed by `route.upstream_base`, provider-level) — unchanged mechanism, but blast radius shrinks: today ~44/50 pools share the `-or` route and cool together; under 4 tiers, cooldown scope is still provider-level but there are far fewer pool objects to reason about when explaining "why did everything using openrouter just go quiet."
- `X-Charon-Provider`/`X-Charon-Failovers`/`/charon/status` — pool-id renames in the payload; any header-scraping tooling downstream needs the new tier-id vocabulary.
- **The incompatible second consumer**: `src/charon/pools.py`'s strict ACP-orchestrator `load_pools`/`choose_from_pool` (requires a mandatory `"agent"` field, currently never fed gateway-schema data — `gateway._tier_pools`'s own docstring already warns "the strict pools.load_pools / ACP-router loader must never see web-authored tier data... it would crash that path"). This redesign must keep that separation explicit and NOT accidentally point the new grades table at this loader without adding the `"agent"` field it requires.
- **The 3 unlinked curated-list concepts** (gateway pools, opencode's `charon`/`charon-full` mirror via `regen-charon-models.sh`, `model_catalog.py`'s 15-entry CLI catalog) — this redesign is the forcing function to unify them: the grades table becomes the SINGLE source; opencode's mirror and the CLI catalog become *views* generated from it, not independently maintained lists.
- Keep-serving-during-migration: the live 4-LOM gateway must not go dark mid-migration; the setup API and `/data` persistence must accept both schemas during a transition window (or the migration must be a single atomic cutover with a verified rollback snapshot, per the `zen-demote`/`dead-free-go-prune` backup discipline already established).

### Phased migration (proposed, 4 phases)

**Phase 1 — Grades table + tier derivation, dark launch (no routing change).** Build the `model → {tier, work_class_grades, cost, health}` table and the tier-membership derivation from benchmark-v2 + models.dev import. Populate it fully for the current 201-route catalog. Ship the anti-duplication preflight detector (see Mechanization). Nothing in the live routing path reads it yet — this phase is provably correct against RouterBench + a shadow-mode comparison against today's pool ordering before anything switches over.

**Phase 2 — Routing algorithm behind a flag, shadow-validated.** Implement the derived-routing algorithm (tier lookup → work-class rank → live-health tiebreak → cascade) as an alternate path in `gateway._build_routes_and_pools`, gated off by default. Run it in shadow (log what it *would* pick, don't act on it) against live traffic for a defined window; diff against actual pool-based decisions; require the proof-of-effect acceptance gate (below) to pass on the shadow data before flipping the flag.

**Phase 3 — Cutover + unify the 3 lists.** Flip the flag; `pools.json`'s 50-entry shape is regenerated as exactly 4 tier sets (or retired in favor of the grades table directly, per the setup-API redesign). `regen-charon-models.sh`'s opencode mirror and `model_catalog.py`'s CLI catalog become generated views off the grades table, closing the 3-lists drift gap. Setup API + dashboard UI migrate to grades-table CRUD. Take a full `/data` backup before cutover (existing discipline from `zen-demote-report.md`/`dead-free-go-prune-report.md`) and verify rollback works before the live 4-LOM gateway is touched.

**Phase 4 — Live actuals/health ledger + retire the inert `cost_rank` formula path.** Land the local JSONL/SQLite per-attempt ledger (Unify/TokenWise pattern), wire it as the live-health tiebreak, and delete the now-dead `derived_cost_rank`-on-`1000`-default code path and any list-order-as-priority reliance — closing the SR-6 inert-feature precedent for good. Confirm via the anti-duplication detector that zero hand-authored per-model pool artifacts remain anywhere in `/data` or git.

## Mechanization — executable acceptance gates

Per the operator's standing requirement that plans stick and don't go inert (SR-6 precedent: a real signal shipped and sat inert for months because nothing gated on it being real). Each criterion below is a concrete test/detector, not prose:

**(a) Proof-of-effect — tier/grades are real for ≥X% of routes (fails if inert).**
Detector: a CI/preflight check computes, over the live grades table, `pct_differentiated = count(routes where work_class_grades is not all-null AND cost_rank != inert_default) / count(routes)`. Gate fails if `pct_differentiated < 90%` (X=90, tune during Phase 1 population). This is the direct fix for SR-6's failure mode: `derived_cost_rank` shipped and nothing ever asserted it was actually producing differentiated values on live data — this gate makes that assertion executable and blocking.

**(b) DRY/anti-boilerplate — ZERO hand-authored per-model pools, enforced by a preflight duplication detector.**
Detector: a script scans whatever config surface remains post-migration (grades table + any residual pool file) for **structural duplication** — two or more entries whose provider-route shape (suffix pattern: bare/`-go`/`-ng`/`-or`/etc.) is identical modulo model name, which is exactly the signature `pools-analysis.md §2` measured (82% shape-duplication). Gate fails on any detected duplicate-shape cluster ≥ N (N=2) that isn't explained by an explicit per-model override annotation. This is a mechanical re-run of the same duplication analysis that produced the sprawl table in `pools-analysis.md`, wired as a standing gate instead of a one-off audit.

**(c) The 3 model-lists unify to 1 (assertion).**
Detector: an integration test asserts `set(opencode_mirror_ids) ⊆ set(grades_table_ids)` and `set(model_catalog_ids) ⊆ set(grades_table_ids)`, and that both the opencode mirror and the CLI catalog are **generated artifacts** (checksummed against a `generated-from: grades_table@<hash>` marker) rather than independently hand-edited files. Gate fails if either list contains an id absent from the grades table, or if either file's content doesn't match a fresh regeneration (drift detector, same class of check `dead-free-go-prune-report.md` had to do manually).

**(d) Commit+SHA-verify + adversarial-review as required plan steps.**
Every phase above (1–4) ends with: a commit whose SHA is recorded in the phase's report, a `zen-demote`/`dead-free-go-prune`-style before/after `/data` snapshot diff for any phase touching live state, and an adversarial review pass (per "Adversarial review default for droid PRs" — downgrades stated not silent) before the NEXT phase starts. No phase is "done" without its SHA and review recorded; this is the same discipline already used for the live pool edits this ADR is replacing, applied to the replacement itself.

## Recommended decision + why it beats the alternatives + honest risks

**Recommended: build the 4-tier + grades-table + work-class design (this ADR's Decision section), executed via the 4-phase migration above, gated by acceptance criteria (a)–(d).**

**Why it beats Option A (generate-50-pools):** Option A optimizes authoring cost but leaves the structural complaint (too many pool *objects* for every future feature — grades, health, work-class — to be retrofitted onto) unsolved, and does nothing for the inert-priority-signal problem. The 4-tier design collapses both the authoring cost AND the object count AND gives cost/priority an explicit, benchmark-backed home instead of a hidden array-order hack.

**Why it beats leaning on a SaaS router (Unify/Not Diamond/Requesty/OpenRouter `auto`):** none are self-hostable with the needed transparency, none satisfy the provider-agnostic/no-hosted-dependency constraint, and OpenRouter `auto` specifically would cap Charon's routing quality to a smaller curated pool than it already has direct access to. Charon must build this in-tree; the survey (`research-gateway-landscape.md`) confirms nobody ships this as a self-hostable product — that gap is the whole rationale for building it.

**Why it beats doing nothing:** the sprawl is actively costing operator time today (evidenced by the `zen-demote`/`dead-free-go-prune` single-pool hand-edit sessions, each a multi-step backup+curl+verify operation for a 1-2-pool change) and getting worse linearly with every new model/provider added (INV-P0 is currently violated in spirit — adding a model is ~5 boilerplate config writes, not "config, not code" in any meaningful sense).

**Honest risks:**
- **Work-class classification is the least-proven piece.** Arch-Router's 93.17% accuracy is against its own paper's taxonomy, not Charon's S0–S6; it needs its own validation pass before Phase 2's shadow-mode flag can be trusted, and the GENERALIST fallback exists specifically because this risk is real, not hypothetical.
- **Benchmark-v2 coverage is still thin.** Only 4 models have been run through the full S0–S6 harness as of this writing (gpt-5.4, glm-5.2, hy3-preview-or, kimi-k2.6) against 201 live routes — most of the grades table's `work_class_grades` will start `null` and fall back to public-benchmark or generalist scores; Phase 1's "populate fully" claim needs an honest asterisk that "fully populated" initially means "tier-only, work-class grades thin" for the long tail.
- **The live-health ledger (Phase 4) is new code with no precedent in Charon today** — it's the piece most likely to need its own design pass rather than dropping straight from this ADR into implementation; treat Phase 4 as the least-specified phase on purpose (a second-pass ADR/ticket is a legitimate outcome, not a plan failure).
- **Repeating SR-6 is the single biggest risk in this whole redesign** — a beautifully designed grades table that ships and then silently stays `null`/inert (e.g. because `add_model`-equivalent tooling doesn't populate it, exactly as `add_models_bulk` didn't stamp real `cost_rank`) would recreate the exact problem this ADR exists to fix, just with a fancier schema. Acceptance gate (a) exists specifically to make that failure mode structurally impossible to ship silently — it is the single most important gate in this document and should be the adversarial reviewer's first target.
- **Migration risk to the live 4-LOM gateway** — this is a schema change to a system currently serving real traffic; Phase 3's cutover is the highest-blast-radius step in the whole plan and must not proceed without the backup+rollback discipline already established in `zen-demote-report.md`/`dead-free-go-prune-report.md`, scaled up from "reorder one pool" to "replace the whole schema."
