## INCIDENT — gpt-5.5 "Model not supported" failure / 2026-07-04 (operator: session was started with gpt-5.5 as the opencode model; opencode errored "Model gpt-5.5 is not supported"; operator switched to glm-5.2 to continue)

### What happened

The operator started this session with `gpt-5.5` as the opencode model. After working through the decision dialogue and into implementation, opencode emitted `Model gpt-5.5 is not supported` and stopped. The operator switched to `glm-5.2` and asked for read-only investigation.

### Verified root cause (live-tested against 4-LOM gateway)

The `gpt-5.5` pool on 4-LOM is ordered `["gpt-5.5-or", "gpt-5.5-ng", "gpt-5.5", "gpt-5.5-go"]`.
I tested each member individually via the gateway:

| Pool member | Provider | Live result | HTTP |
|---|---|---|---|
| `gpt-5.5-or` | openrouter | `Insufficient credits` | **402** |
| `gpt-5.5-ng` | nanogpt | **works** ("Hi!") | 200 |
| `gpt-5.5` (bare) | opencode-zen | **depleted** (operator: $2.99 → -0.04) | — |
| `gpt-5.5-go` | opencode-go | `Model gpt-5.5 is not supported` | **401** |

So: OpenRouter is out of credits, opencode-zen is depleted, opencode-go rejects `gpt-5.5` as
not-in-its-catalog. Only NanoGPT (second in the pool) actually serves the model. The error
the operator saw was opencode-go's raw 401 body, relayed verbatim by the gateway after the
failover loop exhausted/terminated.

### Two distinct bugs

**BUG 1 — Pool ordering:** NanoGPT (the intended primary/anchor, $12/mo flat, working) is
**second** in the `gpt-5.5` pool, not first. OpenRouter (no credits) and opencode-zen
(depleted $2.99) are ranked ahead of it. Only `deepseek-v4-pro` was restored to
NanoGPT-primary per the prior handoff; `gpt-5.5` and other branded pools were NOT.
POOLS-EDIT-PLAN.md explicitly excluded `gpt-5*` pools from reordering ("branded premium
pools — LEAVE"), which preserved the broken order. The operator expected NanoGPT as the
default provider; the live config does not reflect that for `gpt-5.5`.

**BUG 2 — Exhaustion misclassification + raw error relay:** The gateway's failover did not
communicate "all providers exhausted" — instead it surfaced opencode-go's raw 401
`"Model gpt-5.5 is not supported"` error to the client. Verified in source:
- `src/charon/proxy.py:31`: `_EXHAUSTION_STATUSES = {429, 402, 503}` — 401 is NOT in the set.
- `_is_billing_error()` catches 401 + billing body patterns; `_is_auth_error()` catches
  401 + auth body patterns. But opencode-go's 401 body (`"Model gpt-5.5 is not supported"`)
  matches **neither** set → `obs.failover=False` → the loop does NOT advance →
  `proxy_server.py:751-756` relays the raw 401 body to the client.
- There is **no synthesized "all providers exhausted" terminal error** — the client always
  sees the last-tried provider's raw error body. The only exhaustion signal is the
  `X-Charon-Failover-Reasons` header, which opencode does not surface to the user.

**The discrepancy the operator flagged:** the error should have indicated "out of balance"
or "all providers exhausted," not "Model not supported." The operator is correct — the
gateway has the information (it tried multiple providers) but discards it and relays the
last raw error. This is a T0-failover regression: the exhaustion-classification gap for
non-billing/non-auth 401s was never closed.
