read-only via `docker exec charon-gateway-1 cat /data/<file>` on 10.0.1.60

opencode-zen/opencode-go later in the tie-break order — see §3). No writes made

### Suffix key
`(bare)`=opencode-zen anchor, `-go`=opencode-go, `-ng`=nanogpt, `-or`=openrouter,

model routed through the same 4 providers (despite `free:false`).

## 2. Duplicate / near-duplicate chains — the suffix-variant pattern

Grouping the 49 non-`auto` pools by their member **suffix shape** (i.e. ignoring
the model name, just "which providers does this pool fan out to"):

| Shape | # pools | % of 49 |
|---|---|---|
| `{bare, -go, -ng, -or}` | **35** | 71% |
| `{bare, -free-go, -free-ng, -free-or}` | 5 | 10% |
| `{bare, -go, -ng, -nw, -or}` (adds neuralwatt) | 2 | 4% |
| `{bare, -ds, -go, -ng, -or}` (adds deepseek direct) | 2 | 4% |
| `{bare, -go, -or}` (missing nanogpt) | 2 | 4% |
| `{bare, -go}` (zen-only, dead-end) | 2 | 4% |
| `{bare, -free-ng, -free-or}` (3-member outlier) | 1 | 2% |

**82% of the 50 pools (40/49 non-`auto`) are one of exactly two templates**
applied per model: `{zen, go, nanogpt, openrouter}` or the same 4-way fan-out
for a `-free`-*named* model. The pool list is essentially **(≈46 curated model
families) × (2–5 provider routes each), flattened into 50 hand-authored JSON
array entries** — confirming the suspected shape. Adding a new model to the
catalog today means hand-writing ~4 `models.json` entries + 1 pool entry that's
90% boilerplate of the same template.

## 3. What client-facing names map to

Three **separate, not-mechanically-linked** "curated" concepts coexist:

1. **The 50 gateway pools themselves** (`pools.json`) — the auto-routing/failover
   unit; a request for model id `X` resolves via `GatewayProxyServer.chain_for`
   → `pools[X]` if `X` is a pool id, else a single route.
2. **opencode's `/model` picker** — two synthetic provider profiles, `charon`
   (curated, currently **30** ids) and `charon-full` (all live models, currently
   **~201–207** ids, drifts with every gateway config change). Generated by
   `~/.config/opencode/regen-charon-models.sh` (client-side, lives in the
   opencode config dir on the operator's machine, not in this repo or the fleet
   dir) from `provider.charon(-full).options.*` in `opencode.json`
   (`PROVIDER_KEYS = ("charon", "charon-full")` in
   `fleet/benchmark/lib/charon_cost.py:62`). **opencode only reads config at
   process start** — per `fleet/HANDOFF-2026-07-06.md:25`, a full
   `pkill opencode && opencode` (not `-f`) is required after regen.
3. **`src/charon/model_catalog.py`'s `_CATALOG`** — a THIRD, independent curated
   list (15 entries: 4 high / 7 med / 5 low `tier_hint` rows) used only by
   `charon tier`/`charon setup`'s CLI catalog picker
   (`cli.py` lines ~782/913/1721/1739). It is a hand-maintained Python tuple,
   unrelated to `pools.json`/`models.json` — a model can be in the gateway pools
   and absent from this catalog, or vice versa.

None of the three is derived from either of the others; keeping them in sync is
manual. `fleet/scratch/dead-free-go-prune-report.md` and
`fleet/scratch/reds-triage.md` are existing evidence of drift between (1) and
(2) (a removal from the curated `charon`=30 list that didn't propagate to
`charon-full`, or vice versa).

## 4. Blast-radius map

What currently depends on the pool *structure* (`pools.json` shape / pool ids /
member format) — i.e., what a redesign puts at risk:

- **`gateway._build_routes_and_pools`** (`src/charon/gateway.py:113`) — the
  compiler every other consumer sits on top of. Reads `pool_map` (role/vid →
  `[model id]`), filters premium-gated members, sorts
  `(not free, derived_cost_rank)` **stable** (so **list order in `pools.json`
  is a live tie-break signal**, not decoration — see below).
- **`derived_cost_rank`** (`src/charon/pools.py:62`) — nearly every entry in the
  live `models.json` has **no explicit pricing and no explicit `cost_rank`**, so
  it falls through to the neutral **1000** default. Only 9 of 201 routes have a
  differentiated rank (10/20/30/40/50/100/120/150). Since `cost_rank` ties at
  1000 for ~95% of routes, **the real per-pool priority signal is the raw
  member-array order in `pools.json`**, not `cost_rank`. This is exactly why
  the "zen-demote" backup exists — demoting opencode-zen/opencode-go priority
  required hand-reordering JSON array elements (membership unchanged, only
  order), because `cost_rank` doesn't express it. Any pool-structure redesign
  MUST decide what carries priority intent going forward (list order vs. a real
  `cost_rank`) or it will silently re-flatten this manually-tuned ordering.
- **`_tier_pools`** (`gateway.py:167`) — a SECOND pool compiler, layered on the
  SAME `_build_routes_and_pools`, fed from the separate `tiers.json` store
  (`config.load_tiers()`, web-authored). Merges into the final `pools` dict with
  `pools.json` vids winning on name collision. A redesign of `pools.json`'s
  shape also has to keep this merge point working.
- **Global fallback providers** (`gateway.load_config`, lines 236–258) — appended
  to the END of every existing pool chain, and synthesizes a `[route] +
  fallback` pool for any single-route model **not already** in `pools`. Changing
  which model ids are/aren't pool members changes which models silently gain
  this fallback.
- **`/charon/{providers,models,pools,tiers,fallback,enable,disable,remove}` setup
  API** (`gateway.make_setup_handler`, `gateway.py:430`) — web-driven CRUD that
  reads/writes `pools.json`/`models.json`/`providers.json` in their CURRENT flat
  schema via `config.set_pool` / `config.add_model` / `config.remove`, then hot
  `_reload()`s the live server. Any schema change (e.g. collapsing the 40
  boilerplate pools into a generic "model × provider-priority-template" model)
  must either keep this API's request/response shape compatible or migrate the
  setup UI (`_SETUP_HTML` inline JS in `proxy_server.py`) alongside it.
- **`GatewayProxyServer.apply_routes`/`chain_for`/`order_by_cooldown`/
  `set_cooldown`** (`proxy_server.py:1100-1155`) — cooldown is keyed by
  **`route.upstream_base`** (provider-level, not model- or pool-level), so a
  429 on one pool's `-or` member cools EVERY pool's `-or` member simultaneously.
  A redesign that changes pool membership doesn't change this cooldown scope,
  but it changes how many pools/models are affected by one provider's cooldown
  at once — currently ~44 pools share the openrouter (`-or`) route and would all
  cool together.
- **`X-Charon-Provider` / `X-Charon-Failovers` / console `/charon/status`
  pools table** — `status_snapshot()` (`proxy_server.py:1190`) renders
  `pools[vid] = [r.label for r in chain]` directly; a pool-id rename/restructure
  changes what the operator-facing dashboard and any header-scraping tooling
  sees.
- **A SEPARATE, incompatible consumer of the same filenames**: `src/charon/
  pools.py`'s `load_pools`/`choose_from_pool` (the strict ACP-orchestrator pool
  loader, `PoolEntry` requiring a mandatory `"agent"` field) reads `models.json`
  + `pools.json` from a state dir and **raises `PoolConfigError`** on any entry
  missing `"agent"`. The current gateway-schema `models.json` (all entries use
  `provider`/`upstream_model`, none carry `"agent"`) would **crash this loader**
  if ever pointed at it — `gateway._tier_pools`'s docstring explicitly calls
  this out ("the strict pools.load_pools / ACP-router loader must never see
  web-authored tier data ... it would crash that path"). A pool-structure
  redesign needs to keep straight which of the two schemas/consumers it's
  targeting.
- **`regen-charon-models.sh` → `opencode.json` `charon`/`charon-full` mirror**
  (client-side, outside this repo) — reads the gateway's live model/pool list to
  populate the two opencode provider profiles; pool-id renames or count changes
  flow through on next regen + full opencode restart, but the **curated `charon`
  =30 list is hand-picked** and does NOT auto-track `pools.json` membership, so
  a restructure can silently orphan entries in one list and not the other (see
  §3, and the drift already logged in `dead-free-go-prune-report.md`).
- **Benchmark harness** (`fleet/benchmark/bench.sh` + `lib/charon_cost.py`,
  `lib/detect_model.py`) — auto-detects "the currently selected opencode model"
  from the opencode session DB, keys usage/cost lookups off `_PROVIDER_KEYS =
  ("charon", "charon-full")`, and records results per model id into
  `model-scorecard.tsv`. It selects models via the opencode picker (§3, item 2),
  so it inherits any drift or restructuring there one hop removed from
  `pools.json` itself.
- **`/data` persistence** — `load_config(state_dir=...)` reads
  `models.json`/`pools.json`/`providers.json`/`gateway.json` as sibling flat
  files in one directory (the mounted `charon_charon-config` volume); `
  _module_inst` reads further sibling `<name>.json` files (cache/guardrails/
  observability/quality/spend/inspector/session_affinity/vkeys/policy) from the
  SAME directory. `apply_routes()` swaps `routes`+`pools` atomically under
  `_cooldown_lock` on hot-reload — a hand-edit of `pools.json` outside the
  `/charon/setup` write path (i.e. not through `config.set_pool`) risks a
  malformed or half-written file being read on the next reload/restart, since
  there's no schema validation on that path beyond "trust the JSON."

## 5. Top sources of unnecessary complexity (my read)

1. **The 4-provider-route fan-out is hard-authored per model, not generic.**
   82% of pools (40/49) are one of exactly two boilerplate templates
   (`{zen,go,ng,or}` or the `-free`-named variant of the same). This is pure
   authoring/config sprawl, not routing logic — a "for any model, try
   [zen → go → nanogpt → openrouter] unless overridden" default rule would
   collapse ~40 of the 50 pool entries and the ~160 boilerplate `models.json`
   route entries they depend on into one small template + a short override
   list, with zero loss of routing behavior.
2. **`cost_rank` is inert for ~95% of routes, so list ORDER silently carries the
   real priority signal.** Since almost everything sits at the `1000` fallback,
   "cheapest-first" is mostly cosmetic; what actually determines routing
   preference today is the hand-maintained array order in `pools.json` (proven
   by the existence of the "zen-demote" snapshot — a whole backup taken just to
   reorder array elements). This conflates two concerns — genuine cost ranking
   and provider-preference/reliability ranking — into one under-populated field
   plus an implicit, undocumented list-order hack.
3. **Two pools (`big-pickle`, `gpt-5.3-codex-spark`) provide no real failover** —
   both members are opencode-zen-account routes (zen + zen's own `-go` alias),
   not independent providers, so they don't deliver the cross-provider
   resilience the pool mechanism exists for; they're artifacts of a model only
   being available from one vendor account.
4. **(bonus) Three independent "curated model list" concepts** (gateway pools,
   opencode's `charon`/`charon-full`, `model_catalog.py`'s 15-entry tier
   catalog) with no enforced relationship — exactly the class of drift already
   being chased in `dead-free-go-prune-report.md` / `reds-triage.md` /
   `MISSING-MODELS-PROVIDERS.md`. A redesign that doesn't also unify or
   explicitly bridge these three will keep generating that drift.
