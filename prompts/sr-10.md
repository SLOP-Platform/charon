# SR-10 — deploy hygiene: ONE producer in the deploy compose (no path to drift)

## ⚠ THE HARD RULE (non-negotiable — this IS the ticket)
**The deploy `docker-compose.yml` must contain EXACTLY ONE producer — never both `build:` and
`image:`.** Two producers can diverge, so the deploy box could run something different from the
CI-tested artifact. That is forbidden. The single-producer rule is the whole ticket; it is not a
suggestion and cannot be traded away. (The earlier base-`image:` + override-`build:` split is REJECTED
— it still leaves two producers that can drift.)

## ⚠ THE ONLY OPEN DECISION IS DECISION-GATED — which single source?
Pick ONE (operator-gated) BEFORE implementing. Both satisfy the hard rule; they differ only in which
producer survives:

- **RECOMMENDED — image-only, CI as sole producer.** Deploy `docker-compose.yml` has
  `image: ghcr.io/slop-platform/charon:<pinned semver>` and NO `build:`. CI builds + publishes the
  image on version-tag push; tags are treated as IMMUTABLE (never overwritten) — digest-pin
  `@sha256:...` as the max-strength option. The deploy box can only PULL, so it physically cannot build
  something divergent. Hotfixes go through CI (tag → build → pull) — `hotfix/v0.2.1` is already staged
  for exactly this flow. Keeps Charon pull-friendly as a shipped product.
- **ALTERNATIVE — build-only.** Deploy `docker-compose.yml` has `build: .` and NO `image:`. Single
  source = the git checkout; deploy = `git checkout <tag> && docker compose up --build`. Simplest for
  one box; loses end-user pull UX and the CI-tested artifact.

## Shared context (grounding for a fresh session)
The Charon container deploy can DRIFT. `docker-compose.yml` currently carries BOTH `build: .` and a
hardcoded `image: ghcr.io/slop-platform/charon:v0.2.0` — two producers, so "what runs" is ambiguous (a
local build vs a pulled image) and nobody can tell which. `release.yml` only publishes on a manual
GitHub Release (`on: release: types: [published]`), NOT on tag/push, so the published image lags the
code. And nothing surfaces the running build's version/commit. That opacity is exactly why the recent
silent-downgrade balance leak was hard to pin down: prod was on an OLDER build than anyone realized.
Root incident ref: the `_normalize_model_id` / raw-equality silent-downgrade double-bill — fixed by
SR-1 on `feat/prod-install` and backported as `hotfix/v0.2.1` off `v0.2.0`.

## What to build (AFTER the source is chosen)
1. **Enforce the single producer.** Edit deploy `docker-compose.yml` so it has EXACTLY ONE of
   `build:` / `image:` per the chosen option — delete the other. No path may exist to run a divergent
   build.
2. **Semver tags, never `:latest`.** Use `v0.2.1`-style tags (image-only: pin the tag, or digest-pin
   `@sha256:...` for max strength). A floating `:latest` pointer destroys "what's running" + clean
   rollback — the same opacity that hid the leak.
3. **Automate the artifact:** fix `release.yml` to ALSO publish on tag push (add a `push: tags:`
   trigger), so the published image can't lag the code. Treat published tags as immutable.
4. **Version stamp:** bake the git SHA into the image via a Docker build-arg → env `CHARON_BUILD_SHA`
   (Dockerfile `ARG`/`ENV`; pass `--build-arg` from compose/CI).

## ⚠ RIDER — status surfacing is NOT in this ticket (keeps owns disjoint)
Surfacing `CHARON_BUILD_SHA` in `/charon/status` (and the startup banner) requires a ~2-line edit to
`proxy_server.py` (`status_snapshot`). That file is single-owned by the SR-2 → SR-6 → SR-7 → SR-8 chain,
so **SR-10 MUST NOT touch `proxy_server.py`.** Record the status-surfacing change as a RIDER to be
folded into SR-2 (or the next proxy_server.py owner). SR-10 only bakes the env var into the image; the
`/status` read-out lands with the proxy_server owner.
