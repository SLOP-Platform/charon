signed session cookie).

## What to build (stdlib only)
1. **Session key.** New secret `CHARON_SESSION_KEY` (`secrets.token_hex(32)`), auto-generated on first
   start if absent, stored 0600/atomically via the existing secrets writer. SEPARATE from the gateway
   token (rotating the token does NOT log the operator out). (Generation site is in gateway.py/secrets.py
   — coordinate per the scope note; the verify/issue logic lives in proxy_server.py.)
2. **Signed opaque cookie.** `charon_sess = b64url(payload) + "." + b64url(HMAC_SHA256(key, b64url(payload)))`,
   `payload = {"exp": <unix_ts>, "v": 1}`. Verify = split on `.`, constant-time `hmac.compare_digest`
   the MAC, then check `exp`. No PII/username. Sliding refresh: re-issue with new `exp` on each
   authorized GUI request within the refresh window. Attributes: `HttpOnly; SameSite=Lax; Path=/;
   Max-Age=2592000` (30d). No `Secure` (plain http on the LAN would drop it — documented tradeoff).
3. **Surface-aware dispatch** in `_handle`. Compute `path_only` first, then:
   - public GUI routes (no auth): `GET /charon/login` -> serve `_LOGIN_HTML`; `POST /charon/login` ->
     validate + set cookie; `/charon/logout` -> clear cookie, 302 `/charon/login`.
   - gated: `authed = (srv.token is None) or _authorized(srv.token) or (is_gui and _valid_session())`.
     The **session cookie authorizes `/charon/*` ONLY, never `/v1/*`**. On unauth GUI `GET`, 302 ->
     `/charon/login` (a login page, not raw 401 JSON); on `/v1/*`, the unchanged 401 JSON.
4. **Login POST.** Reuse the existing Origin/`Sec-Fetch-Site` CSRF guard; constant-time compare the
   submitted `token` against `srv.token`; on success `Set-Cookie charon_sess`; 302 -> `/charon`; on
   failure re-render `_LOGIN_HTML` with an error, no cookie, no timing leak. The `?token=` path also
   mints `charon_sess` (replacing the raw-token cookie) and 302s to strip the token from the URL (TOFU
   upgrade in one hop). Token stays a valid admin fallback for `/charon/*`.
5. **CLI (`cli.py`).** `charon login` -> resolve token from secrets, print a click-once
   `http://<host>:<port>/charon?token=<token>` (optional `--open`). `charon logout --all` -> rotate
   `CHARON_SESSION_KEY` (invalidate all sessions). Prefer printing `run 'charon login'` over the raw
   `?token=` URL in the banner (closes the ATC token-in-banner finding).

## Acceptance criteria (from AUTH-GUI-DESIGN.md §8, condensed)
1. `/v1/chat/completions` + `/v1/models` behave IDENTICALLY to before with valid/invalid/absent Bearer;
   a session cookie does NOT authorize `/v1/*`.
2. Unauthenticated `GET /charon` (or `/charon/setup`) 302-redirects to `/charon/login` and renders a
   login page (not raw 401 JSON).
3. `POST /charon/login` with the correct token sets an HttpOnly signed `charon_sess` cookie and 302s to
   `/charon`; subsequent `/charon/*` GETs succeed with NO token in URL or header.
4. `POST /charon/login` with a wrong token re-renders the form with an error, sets no cookie, and is
   constant-time (no early return leaking validity).
5. A tampered/expired `charon_sess` is rejected (falls back to login); a valid cookie within the refresh
   window is re-issued (sliding expiry).
6. The gateway token still works as `?token=` and as an admin fallback for `/charon/*`; an old `?token=`
   link auto-upgrades to a `charon_sess` cookie and strips the token from the URL.
7. `charon login` prints a working click-once URL that lands authenticated.
8. `charon logout --all` rotates `CHARON_SESSION_KEY` and invalidates prior cookies.
9. Existing CSRF/Origin and DNS-rebinding guards still pass; `/charon/login` POST is CSRF-guarded.
10. `CHARON_SESSION_KEY` is auto-created 0600 in secrets.json on first start; never logged; never
    forwarded upstream. NO secret VALUES appear in code, tests, prompts, or logs.

## Test plan (stdlib unittest + live loopback server)
- **Unit:** cookie sign/verify round-trip; tamper (flip a MAC byte) -> reject; expired `exp` -> reject;
  sliding re-issue.
- **Integration (spawn GatewayProxyServer on 127.0.0.1):** `/v1/models` with Bearer -> 200; wrong
  Bearer -> 401; with ONLY a session cookie -> 401 (proves API stays token-only). `GET /charon` no creds
  -> 302 `/charon/login`. `POST /charon/login` good token -> `Set-Cookie: charon_sess`; follow-up
  `GET /charon/config` with cookie -> 200. `POST /charon/login` bad token -> form + no cookie. `?token=`
  GET -> sets `charon_sess` + 302 stripping token. Cross-origin `POST /charon/login`
  (bad Origin/Sec-Fetch-Site) -> 403. Loopback bind + non-loopback Host -> 403 (rebinding guard intact).
- **CLI:** `charon login` prints a URL that authenticates end-to-end; `logout --all` rotates the key and
  401s an old cookie.
