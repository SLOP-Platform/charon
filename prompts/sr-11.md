## Shared context (grounding for a fresh session)
All six GitHub Actions in the repo are already SHA-pinned with a trailing `# vX` comment (the
supply-chain posture `docs/SUPPLY-CHAIN.md §5` requires) — but the pins go STALE. They currently lag
the actions' current major/minor SHAs, which is what triggers the **Node-20 deprecation warnings** on
`actions/checkout`, `actions/setup-python`, the `docker/*` actions, and `actions/attest-build-provenance`.
Nothing bumps them. **Dependabot is NOT currently configured** (confirmed: no `.github/dependabot.yml`
exists in the repo).

The fix is a single `.github/dependabot.yml` with `package-ecosystem: github-actions`. Since the
[2022-10-31 changelog](https://github.blog/changelog/2022-10-31-dependabot-now-updates-comments-in-github-actions-workflows-referencing-action-versions/),
Dependabot bumps each action **SHA→new SHA (never SHA→floating `@tag`)** and rewrites the trailing
`# vX` comment to match — so the pins stay full-SHA and the comments stop lying. That clears the
Node-20 deprecations on an ongoing basis WITHOUT weakening the SHA-pin posture. (Comment-rewrite only
fires when the version is at end-of-line; every Charon pin is `…@<sha>  # vN`, so all six qualify.)

Full investigation + citations: `/home/stack/charon-private/fleet/CI-ACTION-BUMP-INVESTIGATION.md`.

## What to build
Add ONE new file, `.github/dependabot.yml`, with exactly this content (from the investigation doc §8):

```yaml
# Mechanizes GitHub Actions version bumps so pinned action SHAs (and their
# trailing `# vX` comments) never go stale — clears Node-20-style deprecations.
# Dependabot bumps SHA -> new SHA (never reverts to a floating @tag) and rewrites
# the trailing version comment to match (comment must be at end-of-line, which all
# of Charon's pins are). See docs/SUPPLY-CHAIN.md §5 — the SHA-pin posture is
# preserved. PR-only (D006 propose-default): a human reviews the SHA and merges.
#
# Scope is github-actions ONLY, deliberately:
#   - docker: the Dockerfile base is a build-arg re-resolved fresh at release time
#     (release.yml `publish`), so a Dockerfile digest pin would fight that design.
#   - pip: the [dev]/[service]/[packaging] extras use open `>=` ranges with no
#     lockfile, so pip version-updates would be near-no-ops here.
version: 2
updates:
  - package-ecosystem: "github-actions"
    directory: "/"                 # scans all of .github/workflows/*.yml
    schedule:
      interval: "weekly"
      day: "monday"
      time: "06:00"
      timezone: "Etc/UTC"
    open-pull-requests-limit: 5
    commit-message:
      prefix: "ci"                 # e.g. "ci(deps): bump actions/checkout ..."
    labels:
      - "dependencies"
      - "github-actions"
    # One grouped PR for all action bumps per week -> minimal review churn,
    # keeps the noise from major-tag SHA moves (dependabot-core#13466) in check.
    groups:
      github-actions:
        patterns:
          - "*"
```

That is the entire change: one new file, no workflow edits, no infra.

## Scope decision — `github-actions` ONLY (record these exclusions)
- **`github-actions` — YES.** The actual pain (Node-20 deprecations) and the clean win.
- **`docker` — NO.** The `Dockerfile` base is a build-arg floating tag (`ARG BASE_IMAGE=python:3.12-slim`)
  and `release.yml`'s `publish` job **re-resolves the live digest fresh at build time** and records it
  in SLSA provenance. A Dependabot `docker` pin would hard-code a `@sha256:…` into the Dockerfile,
  FIGHTING that fresh-resolve design (which is the source of truth). Do NOT add it.
- **`pip` — NO.** The `[dev]`/`[service]`/`[packaging]` extras use open `>=` lower-bound ranges with
  NO lockfile. Dependabot's pip updater only bumps when a newer version violates the constraint (or a
  security advisory), so with open ranges + no lock it opens essentially NO version PRs — config
  surface for ~zero value. Security-only pip alerts are already covered by `pip-audit` in `heavy.yml`.
  Revisit only if these get pinned or a lockfile is added.

## Merge policy — PR-only (no auto-merge)
Fits propose-default landing (D006): Dependabot opens a grouped weekly PR, the full gate runs, a
maintainer reviews the SHA diff and merges. No auto-merge companion workflow. (Auto-merging a hash-pin
bump would land a SHA in `master` without a human reading it — a direct softening of the SHA-pin trust
model; leave it OFF.)

## Self-hosted-runner note (4-lom) — mention, don't act
Two surfaces, kept separate: **(a)** Dependabot's own UPDATE job runs on GitHub-hosted infra (self-hosted
runners are not used by Dependabot on public repos), so the bump computation never touches 4-lom.
**(b)** The CI that runs ON the resulting PR: a Dependabot PR is a SAME-REPO branch, so `ci.yml` runs on
4-lom with the bumped action BEFORE human review. Mitigated by: Dependabot's read-only `GITHUB_TOKEN`
with no secrets on PR runs; secrets/`packages:write` exist only on the `on: release` publish path (never
on a PR); and `pull_request_target` is not used anywhere. The optional actor-aware `runs-on` hardening
(route dependabot PRs to `ubuntu-latest` to keep unvetted action code off 4-lom) is a SEPARATE follow-on
that owns `.github/workflows/*.yml` — noted here but **OUT of this ticket's owns.**
